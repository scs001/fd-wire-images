# 轻量个人 cell 评估备忘（2026-10-11）

**问题**：方向 D（个人工作台——数百信息源、持续迭代、分享、对话 agents）需要
给个人用户单独的 cell 吗？

## 结论

**v1 不建个人 cell，维持共享业务面**（10-11 用户已定调「不建个人 cell，太重」，
本评估确认该决策在当前能力面下仍然成立）。重开的触发条件见文末。

## 依据：个人用户在今天的能力面上能得到什么

| 能力 | 形态 | 对个人的意义 |
|---|---|---|
| 免费档数据面 | 3 数据集 × 10,000 行 × 存储 50MB | 数百源的**聚合结果**可承载（原始全量不可） |
| 上传/CSV 导出 | 双向 | 数据可进可出，无锁定感 |
| 修正编辑 | 表单页（第七轮） | 人工核对/修数 |
| 看板 | AI 生成 + 人工绑定（第八轮）+ 契约确定性刷新 + 定时 | 信息面板全自动更新 |
| 源包 | 目录筛选订阅 | 宏观指标侧的"信息源"由平台供给 |
| 分享 | 签名链接 + 品牌面 | 给别人看 |
| 对话 | ChatPage（壹座 Backend-Auth 回退） | 和 agents 沟通 |

个人场景的真实瓶颈是**源数量 × 源体量**，不是算力——这属于方向 C（panel 供给
引擎）与源包，不是个人存储。给每个人一个引擎 cell 解决的是错问题。

## 若未来要放开：三个梯度的预案

1. **共享面提额**（最轻）：免费档参数化到个人套餐（行数/数据集数/存储随套餐
   调）——`FD_WIRE_FREE_MAX_*` 已是 env，无结构改动。
2. **PG schema-per-user**（中）：wire_datasets PG 实例上按用户开 schema 承载
   个人数据集（api 档路径原样、免引擎）——piggyback 既有双库拓扑，成本≈0，
   不碰引擎。
3. **真个人 cell**（重，不推荐）：引擎物化 per-user——计量/运维/成本全面升维，
   仅在个人用户愿意为「本地级数据体量」付费时才值得。

## 重开触发条件

- 个人用户配额压力成为主要投诉/流失原因（提额解决则停在一档）；
- 出现明确的「个人本地数据 >10k 行且要引擎级查询」的付费需求；
- 源包/爬虫供给线（方向 C）落地后个人源体量真实起飞。
