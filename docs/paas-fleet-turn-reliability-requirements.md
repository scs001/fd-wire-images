# 壹座侧需求：舰队回合可靠性（失败可见性 + 重试语义 + 超时可归因）

> 提出方：fd-wire（柏讯线）
> 日期：2026-10-26
> 依据：`GET /api/fleets`、`GET /api/fleets/<id>`、`GET /api/fleets/<id>/turns` 全量普查（7 支活跃舰队、178 条回合记录，扫描时刻 2026-10-26T03:42Z）
> 关联：`paas-wire-line-install-gate-and-fleet-audit-requirements.md` §五（停机不补跑）、§六（本文的摘要版，建议以本文为准）
> 性质：**不是 wire-content-fleet 的交付缺陷**（该 change 已归档，自身产物/报数/审计判据实证通过）。本文记录的是平台层在无人值守回合上的三个缺口，影响所有舰队线。

---

## 零、结论先行

无人值守舰队现在处于「**跑了但没跑成，界面看不出来**」的状态。实测 178 条回合里 **132 条失败（74%）**，但绝大多数岗位在控制台仍显示 `正常`（`on_duty` + `recent execution within tolerance`）。其中：

- `runtime_not_ready` **69 次**，其中 **58 次耗时 0 秒**（回合根本没启动）；
- 同一秒内重复尝试 **3–9 次**（11 处爆发），说明有重试逻辑但没有间隔/去重；
- `timeout` **27 次**全部卡在 600–616 秒（10 分钟预算硬上限），记录里**不含**最后一步做了什么；
- 某岗位 `consecutiveFailures=12`，状态仍 `on_duty`——平台自己数了 12 次失败，却不影响状态、前端也不展示。

对无人值守产品来说，这比「跑失败并报警」更危险：**假正常**。用户以为每天在跑，实际什么都没产出。

---

## 一、P0 · 回合失败不影响岗位状态，控制台不可见

### 现状（实测）

`GET /api/fleets/<id>` 的岗位对象里，`consecutiveFailures` 是有的，但：

| 舰队 | 岗位 | `consecutiveFailures` | `status` | `statusReason` |
|---|---|---|---|---|
| 柏讯情报舆情舰队 | 投稿岗 | **12** | `on_duty` | recent execution within tolerance |
| 营销·官网内容舰队 | 选题岗 | **4** | `on_duty` | recent execution within tolerance |
| 营销·官网内容舰队 | 审读岗 | 3 | `on_duty` | recent execution within tolerance |
| 识律政心监测舰队 | 指标巡检员 | 2 | `on_duty` | recent execution within tolerance |
| 识律政心监测舰队 | 政心主编 | 2 | `on_duty` | recent execution within tolerance |

判定逻辑看的是「最近一次执行是否在容忍窗内」（`evidence.lastRunAt`），**不看那一轮是否失败**。于是连败 12 轮仍判正常，且 `statusCounts` 里它被计入 `normal`，cockpit 一片绿。

对照：真正的 `missing`（本仓 `wire-content-fleet` 巡线岗）是因为**超 48h 没有报数**才被判出来的——也就是说，只有「连失败但仍在报数」的岗位能一直装正常；一旦失败到连报数都没有了才暴露，且暴露时已经过去两天。

### 需求

1. 岗位状态判定纳入回合结果：连续失败 N 轮（建议 N=3）应降级为「异常/需关注」，与「本轮无信号」明确区分。
2. `consecutiveFailures`、最近一次回合的 `errorKind`、失败起始时间，必须在 fleet cockpit 与岗位卡片可见（目前 API 有、UI 无）。
3. `statusCounts` 的 `normal` 不应包含「最近回合失败」的岗位。

### 验收

造一个连续 3 轮 `runtime_not_ready` 的岗位：它的 cockpit 状态不再是绿色正常，卡片上能看到「连续失败 3 次 · 最近原因 the agent runtime is not ready」；`statusCounts` 把它计入异常而非 normal。

## 二、P0 · 回合未启动（`runtime_not_ready`）语义缺失：0 秒失败、无冷却重试

### 现状（实测）

`runtime_not_ready` 是全平台最高频失败（69/178，39%）。特征极强：

- **耗时恒为 0 秒**：`startedAt == endedAt`（58/69 条）。回合没有真的开始，是**启动阶段**被拒。
- **同一秒内重复 3–9 次**：例如柏讯情报舆情舰队在 `2026-10-24T23:40:58` 同一秒产生 **9 条**失败回合；`22:11:00` 8 条、`22:44:09` 7 条；营销·官网内容舰队 `2026-10-25T08:32:53` 5 条。说明失败后有立即重试，但**没有退避、没有去重**，一次瞬时故障会被记成 N 次失败。
- **横跨 6 支舰队**：识律评测哨、营销·官网内容、lex 营销、识律政心、柏讯情报舆情、柏讯内容都中过。不是单支舰队配置问题。

推断：`runtime_not_ready` 出现在 cell 运行时尚未就绪（pod 启动/重启/会话池未热）时。这与另一条已知事实（`the agent runtime restarted mid-turn`，`other` 类，20 次）是同一族：**平台重启期间无人值守回合被吞**。

### 需求

1. **区分「未启动」与「跑了但失败」**：`runtime_not_ready` 不应生成一条正式回合记录并计入岗位的执行历史/失败计数（或至少单独计数），因为它没有消耗预算、没有产出、也没有副作用。现在它既污染 `consecutiveFailures`，又让 `lastRunAt` 前进（看起来「刚跑过」）。
2. **启动前就绪检查 + 冷却**：触发时若 cell 未就绪，先等就绪（有界等待），或直接推迟到下一周期；同一秒内的重复尝试必须去重，并加最小重试间隔（建议指数退避，起始 ≥30s，上限 ≤5 次）。
3. 失败聚合：同一根因（同 pod 重启窗口、同一秒批次）应聚合成一条「本轮未执行（运行时未就绪）」事件，而不是 N 条失败回合。

### 验收

在 cell 重启窗口内触发一次岗位回合：`turns` 里最多 1 条「未执行」记录（或该类记录独立表），`consecutiveFailures` 不被 N 倍放大，岗位卡片刻度显示「本轮未执行：运行时未就绪（第 k 次）」；下一周期正常执行后自动恢复。

## 三、P1 · `timeout` 不可归因（无耗时进度、无最后动作）

### 现状（实测）

27 次 `timeout`，**全部** 600–616 秒——正好撞 10 分钟回合预算上限。回合记录字段只有 `id, memberId, source, status, errorKind, error, model, startedAt, endedAt, sessionId`：

- 没有「最后成功调用的工具」；
- 没有已执行步数 / token 用量；
- 没有「卡在哪个 MCP 调用」；
- `error` 字段只有 `turn timed out` 五个字。

运营方拿到这个信息无法判断是：模型慢、某个 MCP 工具挂死、prompt 让它做了不该做的事（例如 HTTP 探测），还是预算本身对该任务不够。

实测旁证：`wire-content-fleet` 的巡线 prompt 曾因未约束「禁 HTTP 探测 / N 分钟内收尾」而把 10 分钟预算烧光，是靠改 prompt 解决的——**但如果 timeout 不可归因，运维只能靠猜，同类问题在别的舰队会反复出现**。

### 需求

`timeout` 的回合记录补充（至少）：

1. 最后一次成功调用的工具名 + 调用耗时；
2. 已用步数 / 已用 token；
3. 达到预算上限时的「卡住点」（正在等待的调用）。

进一步（建议）：把 timeout 分成两类——`turn_budget_exceeded`（模型还在正常干活但预算不够）与 `stalled`（某次工具调用长时间无返回），两者运维处置完全不同。

### 验收

构造一次超时（工具 hang 或超长 prompt）：回合记录能看出「卡在 `<tool_name>`，已等 Xs，已走 N 步」，运维据此可判断是加预算还是修工具。

## 四、P1 · `model_upstream` 无熔断/无降级（补充观察）

### 现状（实测）

识律政心监测舰队 14 次 `model_upstream`，全部落在 `2026-10-25T02:30Z → 03:00Z` 的 30 分钟窗口内：`503 Service temporarily unavailable` 与 `502 Upstream service temporarily unavailable`。

期间该舰队其它岗位也在连跑，没有看到熔断或切换 `fallbackModel`（岗位对象有 `fallbackModel` 字段，实测全部为 `null`；`modelNotice` 也全为 `null`）。

### 需求

1. 上游 5xx 连续失败达阈值时，舰队调度应熔断一段时间（避免每轮都撞墙并放大失败计数）；
2. `fallbackModel` 有配置时应真正启用（当前岗位级字段存在但在该窗口未见生效证据），并在回合记录里注明「本轮已降级到 X 模型」；
3. 上游不可用期间的回合不计入岗位健康度（与 §二 同口径：不是岗位的错）。

### 验收

模拟上游持续 5xx 30 分钟：该舰队回合要么明确标注降级模型，要么被熔断并在 cockpit 显示「模型上游不可用，已暂停 N 分钟」；恢复后自动继续。

## 五、影响面与优先级

| # | 问题 | 优先级 | 影响 |
|---|---|---|---|
| §一 | 回合失败不影响状态、UI 不可见 | **P0** | 所有舰队线：假正常，无人发现停摆 |
| §二 | `runtime_not_ready` 0 秒失败、无冷却重试 | **P0** | 69/178 回合（39%），重启期集中爆发 |
| §三 | `timeout` 不可归因 | P1 | 27 次，运维只能猜 |
| §四 | `model_upstream` 无熔断/无降级 | P1 | 上游抖动放大失败计数 |

本文所有数字取自 2026-10-26T03:42Z 单次普查（178 条回合、7 支活跃舰队）。**§一 与 §二 是本轮最该先修的**：它们叠加起来，会让「舰队没在干活」这件事在控制台上完全看不出来——这是无人值守产品最不能接受的失效模式。
