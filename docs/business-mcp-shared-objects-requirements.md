## 一、背景（一段话）

柏讯本体建设 v1 把**客户自有数据**的对象世界做实了（声明→确认落库→对象三端点
→m:n 物化）。但「本体」更大的存量在共享源：年鉴概念登记 20,375 条（`yb.<domain>.<code>`）、
industry 实体 55 个、法律 KG legal_v2（71,646 节点）、gov_v3（212 篇车道）——这些
语义资产散在 DAAS/KG 各自仓里，柏讯对象面**吃不到**，business-mcp 也只给了搜索腿
（`ai_search` / `graph_search`）。客户数据与共享源在同一对象世界里互相引用
（客户的「宜昌」该等于年鉴的哪个区域实体？客户的行业分类该归到哪个 industry 实体？）
——这一步不做，柏讯的本体只是每 cell 一座孤岛。

## 三、需求（请裁决/请对齐）

### R1 · 共享对象的归属裁决（本件的核心题）

「共享源对象面」落在哪，三案请拍：

| 案 | 形状 | 代价 |
|---|---|---|
| A 归 business-mcp | 把 `graph_search` 扩出对象形状读工具（search/get/relations 三件套，与 `wire_object_*` verb_noun 形状逐字对称） | business-mcp 侧新施工；两仓工具形状纪律须对齐（命名、返回包络、分页口径） |
| B 归柏讯镜像 | 共享概念镜像为柏讯侧实体声明（走 v2 对象面既有读路径） | 数据复制 20,375+ 条与同步腿；违背「柏讯不重复建共享面」定位 |
| C 混合（提出方倾向） | **共享对象读面归 business-mcp**（A 案形状），**联面归柏讯**：客户数据集引用共享实体经柏讯物化腿 join（见 R2）；柏讯对象面不把共享源复制进来，只在血缘/注记层引用 | 两侧各施工一小块；职责与判定表「共享源搜索在 business-mcp」的既有精神一致 |

### R2 · 跨面关系：客户实体引用共享实体

现 entity-layer 纪律「两端实体须同属本企业」是 cell 隔离正确姿势，但挡住了
「客户的订单.地区码 →(n:1) 年鉴.区域实体」。请裁形态，两候选：

- **external_ref 实体**：一等实体新类型，绑定=外部源引用（registryName+概念码），
  不入 cell 数据集；图谱可画、`wire_object_relations` 可沿（读腿转 business-mcp
  共享面取数，计量归属=共享源轨）；校验纪律：列⊆快照仍成立。
- **declared_view 物化视图**：不改实体模型；在 transform 腿把共享源按声明
  物化进 cell 为 derived 数据集，再按既有 n:1 关系绑定。零新语义、但数据要落 cell
  （体量/新鲜度/档位三账）。

提出方倾向 **external_ref**：declared_view 把 20,375 条年鉴灌进每 cell 的存储账
不成立（体量），且新鲜度只能靠重派生；external_ref 是「关系指向身份」纪律的自然延伸。
此题归柏讯仓施工面，但**须与 R1 同批裁**（两题共用量词：客户对象沿关系够得着
共享对象，才算一个对象世界）。

### R3 · 形状对齐纪律（随 R1 落地）

若 R1 取 A/C：business-mcp 共享对象三件套与 `wire_object_*` 的 verb_noun、
分页/包络/404-vs-empty 纪律逐字对称（客户集群岗位一套消费姿势吃两面），
命名提案：`graph_object_search` / `graph_object_get` / `graph_object_relations`
（沿 graph_ 域前缀既有形）。工具面风险标签只复用 read/write 既有值
（沿 MCP 工具面治理口径），不造新枚举。

## 四、明确不在本件范围

- 共享源数据本身的爬取/质量（DAAS 线既有活）
- 客户 cell 的开通与真实客户接入（本体建设 v1 已裁：v2 议题）
- 法律 KG 的图查询面扩展（KG 车道自有 spec，与本件只在「形状对称」处相交）
