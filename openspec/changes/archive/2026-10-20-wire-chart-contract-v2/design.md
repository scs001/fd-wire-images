## Context

见 `proposal.md` — Why。塑造本设计的技术现状：

- 渲染器已具备承载任意图表配置的能力：`DashboardRenderer.tsx` 的 `EChartBox`
  接受完整 option 并做 init/dispose/option 重画/窗口自适应（固定 SVG 渲染器，
  测试环境无 canvas 也能跑）。真正的天花板在它上游的 `ChartBody`：`xAxis` 硬编码
  `type: "category"`、第 0 列当 x 轴、其余列一律成系列、图高写死 220。
- 契约是前端单方解析：`spec.ts` 的 `parseDashboardSpec` 做宽容归一，后端
  `validate_kind_spec` 对 dashboard 只走通用层（title 非空 + spec 非空对象）。
  **扩 v2 不需要后端结构校验改动**，这是本设计最大的成本优势。
- 刷新契约已经天然保表达力：`query_contract.py` 的回写是
  `panel["snapshot"] = snapshot`，注释明确"面板其余字段不动"。v2 字段因此
  不需要刷新侧任何新逻辑，只需处理 `raw_option` 的 kept 判定。
- 存量成品看板（`finddata/dashboards/*.spec.json`）用完整 echarts option，
  实测只用到 `axisPointer / grid / legend / logBase / markLine / series /
  symbol / tooltip / xAxis / yAxis` 这些键，**函数型字段仅 4 处且全为恒等
  `(v) => v`** —— 说明 JSON 直通几乎无损，逃生舱方案在数据上已被验证可行。
- 编辑器当前形态：面板增删/移序/span/标题/source/config + 类型互转 + 复制 +
  查询绑定表单。v2 需要嵌入编码通道与叠加层的表单，但不该膨胀成图表 IDE。

## Goals / Non-Goals

**Goals:**

- 让契约容得下"专业图表"：时间轴、多轴、副图分区、阈值线与事件标记、
  以及类型化字段覆盖不到的任意图形（逃生舱）。
- 一次性打通三个下游场景的公共地基：存量成品看板迁入、行业看板批量上架、
  AI 浮层里"帮我改这张图"。
- 保持 v1 零漂移：存量产物、分享链接、市场摘要、刷新语义全部不变。
- 把"看起来像玩具"的视觉短板一并收口：图高、缩放、十字光标、全屏、图数切换。

**Non-Goals:**

- 不做图表 IDE。用户可编辑的是类型化子集；`raw_option` 面板只读结构查看。
  手写完整图表配置不是产品能力。
- 不做看板级布局引擎（自由拖拽/任意栅格/响应式断点重排）。仍是 3 列栅格 ×
  span 1/2/3 × 可声明高度，只把"高度"从写死变成可声明。
- 不做实时流式图表、不做图表联动钻取（点柱子跳明细）。属后续能力。
- 不改 `finddata/dashboards/` 的迁移执行——本变更只负责让契约容得下它们，
  迁入脚本归 `wire-showcase-market`。
- 不引入新依赖。全部能力为 echarts 5.6 原生特性。

## Decisions

### D1：v1 与 v2 是同一份解析器的两个分支，不是两套类型

`parseDashboardSpec` 产出统一的面板类型，v2 字段全部可选；"是不是 v1 面板"
由字段存在性判定（有 `encoding`/`panes`/`overlays`/`raw_option` 才是 v2 形态），
渲染时无 v2 字段即走既有的"第一列当 x"回退分支。

**为什么不新建 v3 或换 spec 版本号**：产物信封的形状由后端最小校验固定，前端
单方解析；引入版本号会让分享页、市场、刷新三处都要分支。字段存在性判定是零
迁移成本的路。

**代价**：v2 的校验分散在字段级归一函数里，没有一处集中的 schema。用
`normalize*` 系列的宽容约定统一（与既有 `normalizeSnapshot`/`normalizePanelQuery`
同款风格）来抵消。

### D2：`raw_option` 与编码通道共存时，编码通道优先

渲染时先生成类型化 option，再用 `raw_option` 做深合并（类型化字段赢、缺位补齐）。

**为什么不让 raw 整体覆盖**：编辑器里用户改了轴类型却看不到效果，是最坏的
体验——用户不理解"这个面板是 raw 的所以你的编辑无效"。优先级方向必须让
**用户可编辑的字段永远生效**。

**代价**：合并语义有歧义风险（数组怎么合？）。定为：对象深合、数组整体替换。
在面板详情区显式提示"该面板含高级配置，部分字段可能与表单编辑项重叠，以表单
为准"。

### D3：`raw_option` 的可序列化校验放在解析层，不在渲染层

`parseDashboardSpec` 阶段对 `raw_option` 做深度遍历，检出函数/正则/类实例等
不可序列化值即整块丢弃并记入 `badPanels`。

**为什么在解析层**：渲染层拿到的永远是可序列化的纯数据，`EChartBox` 不必学会
防御；同时"坏面板隔离"这一条既有纪律（不整板失败）自然覆盖。

**这条不是形式主义**：存量成品里有 `(v) => v` 字符串，JSON.parse 出来是字符串
而非函数——会被 echarts 静默忽略或抛错。校验把这类问题在打开看板时暴露成
可见标注，而不是让用户面对一张空白图。

### D4：多窗格用多 grid + 共享 axisPointer，而非嵌套子图

echarts 的标准做法：N 个 `grid` 上下排列、每格一对 xAxis/yAxis、`axisPointer.link`
把十字光标串起来、`dataZoom` 的 `xAxisIndex` 指向全部窗格。

**为什么不用嵌套/独立图表实例再手工同步**：手工同步缩放与光标需要监听事件回写
另一个实例，几十行易错代码换来同样的效果；echarts 原生支持且零同步代码。

**代价**：窗格高度必须自己算（grid 的 top/height 是百分比或像素）。设计上由
面板声明 `panes[].height`（相对权重），渲染器换算成 grid 布局；不声明时主窗格
权重 3、副窗格权重 1。

### D5：工具栏是渲染器的可选 prop，不是默认行为

`<DashboardRenderer spec={...} />` 保持零工具栏（分享页红线靠这个天然守住），
控制台侧显式传 `toolbar` 才渲染。

**为什么不靠路由判定**：渲染器不知道自己在哪。用 prop 把"是否允许工具栏"变成
调用方的显式选择，分享页那条测试断言（渲染器本体零导出入口）继续成立。

**代价**：三个调用点（产物页、分享页、市场渲染）各自要明确传或不传。用
TypeScript 的默认 `false` 兜住——漏传即安全侧。

### D6：图数切换复用既有表格渲染，不新增数据通路

"数据表"视图就是把 `EChartBox` 换成既有的 `TableBody`（同一个 snapshot）。

**为什么**：`TableBody` 已经处理了列头、空值、20 行滚动。零新代码，且保证
"图和表看的是同一份数据"这件事在实现上不可能出错。

`raw_option` 面板的表视图特殊：数据在 option 的 `series[].data` 里，需要按
系列名抽成两列表（x/值）。抽不出来就如实显示"该面板不提供表格视图"。

### D7：AI 生成侧只改指令文案，不改工具 schema

`dashboard_spec_create` 的 parameters 仍是 `{title, spec}`（spec 自由 JSON）。
v2 能力通过 description 里的规范与示例传达。

**为什么不把 v2 拆成结构化 tool schema**：六类面板 × 编码通道 × 窗格 × 叠加层
做成 JSON Schema 会让工具描述膨胀到数千 token，每次对话都付费，且模型对深层
嵌套 schema 的遵从度并不比示例高。给约束 + 好示例是更划算的做法。

**代价**：模型可能产出不合契约的形状。既有三级容错（解析层宽容 + 坏面板隔离 +
不整板失败）已经覆盖；不额外加校验轮。

### D8：类型谱分两档，编辑器按档呈现

**基础档**（kpi/line/bar/table）——保留现有编辑器表单与类型互转；
**高级档**（candlestick/scatter/pie/heatmap/gauge/radar/treemap/sankey/funnel/boxplot）
——可选类型、可编辑编码通道与叠加层，但不做逐类型的专属表单（不做 K 线的
涨跌配色选择器、不做桑基图的节点布局选项）。

**为什么**：逐类型专属表单是图表 IDE 的入口，会把编辑器从 600 行推到数千行，
而真实需求（"这批图表能上来、能改标题能调轴"）不需要它。高级档的表达力靠
`encoding` + `overlays` + 必要时的 `raw_option` 兜住。

## Risks / Trade-offs

- **`raw_option` 成为逃逸口，长期侵蚀类型化契约** → 约定：类型化字段覆盖
  80% 场景；新场景优先扩类型化字段而非鼓励写 raw。在编辑器里 raw 面板显式
  标注"高级配置"而非默认路径，形成使用摩擦。

- **深合并语义在数组上整体替换，可能与用户预期不符**（例如 raw 里配了三条
  markLine，表单里加一条，结果是三条被一条替掉）→ 数组替换语义写进面板
  详情提示文案；`overlays` 走类型化字段时不与 raw 数组混用。

- **多窗格的高度换算在不同面板高度下可能挤压副图**（面板总高 300px 却声明
  3 个窗格）→ 设最小窗格高度下限（如 60px），低于下限时按比例压缩而非塌陷；
  低于总下限时降级为只渲染主窗格并标注。

- **`xAxis.type: "time"` 要求数据是时间值，而快照规定值归 str/number/null** →
  时间轴分支在渲染层把快照首列的字符串按 ISO/`YYYY`/`YYYY-MM` 解析成数值时间戳；
  解析失败的点置 null（echarts 断线而非错位）。这条要在渲染器里显式实现，
  不能让 echarts 自己猜。

- **v2 面板在 AI 契约刷新路径上被 AI 轮改写结构** → AI 刷新轮的指令已明确
  "面板结构一律不动，只更新 snapshot"；v2 字段因此天然存活。补一条断言测试
  锁住这个不变量。

- **工具栏/全屏与 ErrorBoundary 的边界**（全屏时父容器卸载会导致图表实例
  泄漏）→ 全屏用固定定位覆盖层 + 原容器保留（不移动 DOM，只改变容器样式），
  `EChartBox` 的 resize 监听已覆盖尺寸变化。

## Migration Plan

1. **纯增量上线，无数据迁移**：v2 字段全部可选，存量产物解析后仍走 v1 分支，
   渲染结果不变。上线即 v1 与 v2 并存。
2. **回滚策略**：回滚前端镜像即回到纯 v1 解析。已写入 v2 字段的产物在旧版
   渲染器下会被忽略（解析器只读它认识的字段），面板退化为按其 `type` 的
   基础渲染或"无数据"占位——**不崩溃，但表达力丢失**。因此 v2 面板的规模化
   写入（下一变更的批量迁入）应在本变更稳定后再做。
3. **验证顺序**：先让单测锁住"v1 面板渲染结果 byte 级不变"（快照断言），
   再开 v2 能力；分享页/市场/整板导出三处回归在 v2 面板出现前完成。

## Open Questions

- 高级档类型是否需要预设模板（选中 candlestick 时预填一份空 K 线骨架）？
  可以在实现中按"有模板更顺手"的经验取值，不影响契约与任务拆解。
- 全屏查看是否需要隐藏侧栏（让面板占满整页而非仅占内容区）？属视觉决策，
  留给实现阶段与布局变更对齐。
