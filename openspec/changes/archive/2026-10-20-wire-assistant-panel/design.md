# Design — wire-assistant-panel

## Context

见 proposal.md — Why。设计只依赖以下既有事实：

1. `POST /api/v1/ai/conversations/{id}/messages` 是**同步**端点：一次请求内跑完
   最多 `AI_MAX_TURNS`（默认 8）轮 LLM ↔ 工具往返后一次性返回。real 场景下单轮
   可能数十秒。
2. `run_build_loop` 在**任何 LLM 调用之前**先判 `resolve_cell_endpoint(customer_id)`，
   为 None 即回常量文案并 `return`。免费档（`plan_code == free`，无 cell）因此
   连一句自然语言回复都拿不到。
3. 循环里每 `append_message` 都 `db.commit()` 并刷新——消息**逐条落库**，无需
   等整轮结束就能读到。
4. `LlmClient` 协议只有同步 `complete()`；`TokenGatewayLlmClient` 是单个
   `httpx.Client.post`，仓内无任何 SSE/流式实现。
5. 前端 `ChatPage` 当前是纯静态引导卡，不发任何网络请求。

## Goals / Non-Goals

**Goals**

- 免费档客户能用「问」：不依赖 cell 的自然语言帮助。
- 付费档客户能用「做」：在浮层里直接驱动既有构建循环，产物落到既有 draft 暂存。
- 构建过程中浮层有可见进度，而不是长时间静默。
- 浮层出现在控制台所有页面，一处挂载。
- 三级上下文（页签/产物/数据集）让答案落到客户当前所在位置。

**Non-Goals**

- **不做流式（SSE）**。见 D1。
- 不把壹座任何页面 iframe 进柏讯。见 D4。
- 不新增数据库表、不改迁移链。
- 不做浮层的历史会话管理界面（会话列表仍在「AI 构建」整页；浮层只承载当前一轮）。
- 不改动既有构建循环的轮次/限额护栏语义。

## Decisions

### D1 — 用增量轮询代替 SSE

`LlmClient` 只有同步 `complete()`，网关侧也没有流式实现。要做 token 级的流式
输出，需要把 `httpx.Client` 换成 `httpx.stream`、把循环改成生成器、把端点改成
`StreamingResponse`，并新增前端 EventSource 解析——这是一整个独立变更的工作量，
且会同时动到构建循环的核心路径（既有 8 处测试直接依赖其同步语义）。

而循环**每追加一条消息就 commit**，所以「增量读取」已经免费得到了：浮层在轮询
`GET .../messages?after_id=N` 时能看到 assistant 文本轮、tool_trace 轮逐步出现，
用户看到的是「正在查数据…」「正在生成看板…」这类真实进展，而不是死转圈。

**取舍**：没有 token 级打字机效果。但构建轮的实际价值在「它在动、动到哪一步」，
不在逐字显现。若将来要打字机，`after_id` 增量协议不用改，只需把 assistant 轮
改成流式写入——接口已经为它留好了形状。

*备选*：直接上 SSE。否决理由如上——在 `complete()` 同步语义上强加流式，等于把
一个契约问题伪装成 UI 问题，且会连带重写循环的失败处理路径。

### D2 — 问答轨与构建轨是两条独立代码路径，不是同一循环加开关

免费档不该因为「没有 cell」而失去「问」的能力。若在现有 `run_build_loop` 里给
cell 判断加个开关，会让「无工具纯问答」和「有工具可构建」两种语义纠缠在同一个
函数里，既有护栏（未开通常量回复、轮次截断）也会变得难以推理。

因此新增 `answer_question()`：**不碰 ToolExecutor、不碰 cell 解析**，直接
`llm.complete(messages, tools=[])`。工具列表为空是本轨的结构性保证——它想调
工具也没有可调用的工具，不需要靠运行时判断兜底。

*备选*：复用 `run_build_loop` 传空 tools。否决——空 tools 时该函数仍会先查 cell
端点并短路，正是要绕开的那一步。

### D3 — 「问」与「做」由前端档位驱动，后端仍各自强校验

前端已知 `customer.plan_code`（`ConsoleView` 已经在传给 `DatasetsPage`），据此
决定浮层是否展示「做」态入口——避免免费档客户点进去才收到一句「档位不足」。

但**前端不作为安全边界**：构建轨的端点本身就是既有的、对无 cell 客户回常量
文案的实现，不会因为前端隐藏按钮就失去保护。前端只做体验裁剪。

### D4 — 「去壹座」是深链，不是 iframe

用户原始诉求里提了三种可能（AI 浮层 / 壹座登录嵌入 / 打开壹座所有页面）。选择
深链的理由：

- iframe 嵌入壹座会让两个独立部署的会话、CSP、cookie 域、错误处理全部纠缠，
  且壹座页面并非为窄容器设计；
- 柏讯与壹座共用同一 Logto IdP，已有账号的客户点过去即登，中间无二次登录成本；
- 用户要的核心是「不要为了做一件事而整站跳走」——浮层的「问」「做」已经覆盖了
  高频动作，剩下的是低频深度分析，深链是合适的档位。

深链一律 `target="_blank" rel="noopener noreferrer"`，与既有 `ChatPage` 引导卡
一致。

### D5 — 上下文用白名单键值，不回传数据行

浮层知道客户在哪：`{ surface: "console", tab: "datasets", artifact_id?, dataset_id? }`
这类**标识**。后端只接受白名单键，且只把标识转成少量元数据（产物标题、数据集名、
面板数）拼进 system 提示——绝不读数据行、绝不读快照值。

理由：浮层是「指路」场景，知道「你在看某个数据集」就足够答「这个数据集能做什么
图表」；把数据内容塞进提示既无必要，也会把一个导航功能变成数据外泄面。

*校验*：`artifact_id` 必须属于当前客户（复用既有 `get_customer_conversation`
同款的归属校验模式），否则丢弃上下文而不是报错——上下文是锦上添花，不该阻断
主流程。

### D6 — 会话存储复用，不新增表

问答轨与构建轨都写 `ai_conversations` / `ai_messages`。区分靠既有消息角色：
问答轨只产生 `user` + `assistant`，工具留痕（`tool_trace`）只可能来自构建轨。

带来的好处：历史、限额（`AI_DAILY_CONVERSATION_LIMIT` 按 conversation 表计）都
自动共用；坏处是「问」也会消耗每日新开对话数。按 D7 用同一会话承载浮层的多轮
问答来缓解。

### D7 — 浮层只维持一个活会话

浮层打开时按需建会话，之后的多轮问答都追加到同一 `conversation_id`，直到用户
主动「新对话」。这样一次浮层使用只消耗 1 个日限额，而不是每问一句消耗一个。

### D8 — 失败如实，与既有循环同款

LLM 不可达 → 浮层显示「AI 服务调用失败」并保留用户输入可重试；不做乐观假回复。
这与 `_llm_failure_message`「绝不产出半成品」的既有纪律一致。

## Risks / Trade-offs

- **[同步端点 + 长轮询的竞态]** 构建请求未返回时，`after_id` 轮询可能读到
  半轮消息（tool_trace 已落库、终答未到）。→ 以请求完成（或失败）作为终态
  信号，轮询只负责过程中的可见性，不做最终状态的判定。
- **[前端档位显示滞后]** `plan_code` 来自会话建立响应；若客户档位在使用中被
  后台改动，前端仍显示旧态。→ 后端强校验兜底，最坏是一次「档位不足」提示，
  不是越权。
- **[轮询放大请求]** 短轮询在多个浮层同时打开时会叠加。→ 轮询间隔按「有新增
  消息」自适应（连续无新增则退避），并在请求终态后立即停止。
- **[问答轨被当免费推理通道]** 免费档可无限问。→ 复用既有日限额与
  `AI_MAX_TURNS` 语义；问答轨单次只做一次 `complete()`，无工具放大。
- **[上下文注入成为注入面]** 客户可构造 `artifact_id` 猜别人产物。→ 归属校验
  失败即丢弃上下文；且注入内容仅元数据不含数据。

## Migration Plan

无数据迁移。上线即生效：

1. 后端先上（新增端点 + 增量查询参数），旧客户端不受影响。
2. 前端随后上（浮层挂载），旧端点保持不变。
3. 回滚：前端移除挂载点即回到引导卡；后端新端点为新增，回滚不影响既有路径。

## Open Questions
