## Context

见 `proposal.md` — Why。塑造本设计的技术现状：

- 市场内核已完整：`artifacts` 表已有 `visibility`（private/link/directed/market）、
  `access_mode`、`published_at`、`published_version`；`artifact_browse.py` 的
  列表在 SQL 层只查 `visibility='market'`；`resolve_renderable` 已实现「本人 /
  订阅 / 定向授权 / 已批申请」四路准入。**缺的只是「匿名看平台自有内容」这一路。**
- 所有市场端点都挂 `require_console_customer_id`——匿名接入必须走独立路由，
  不能给既有端点加可选鉴权（那会让「忘传 token 就变公开」成为可能的配置事故）。
- 产物归属是 `customer_id: str`（`artifacts.customer_id`），而登录映射到
  `billing_customers`。平台租户只需是一条普通 customer 行，不需要新表。
- 分享通道已有成熟的匿名读范式（`share/routes.py`：secret → 验签 → 钉死版本
  → published 复检 → 统一 404 → 令牌级限流 → 短缓存）。橱窗端点可以照抄这套
  工程骨架，**但不用签名令牌**——它面向公众，不是点对点。
- 成品看板实际只有 `intl-six-country.spec.json` 与 `macro_cn_spec.json` 两份
  保留完整 `charts[].option`（16 张图，已实测 16/16 可经 raw_option 渲染）。

## Goals / Non-Goals

**Goals:**

- 给柏讯开一扇**对外、匿名、可索引**的橱窗，展示平台自有看板与真数据。
- 用最小改动复用既有市场内核（版本链、可见性、渲染器、刷新）——不造第二套。
- 建立**行业看板批量上架**的可重复通道，让 108 个源单元的数据能持续变成看板。
- 红线只放开有界的一格：平台自有内容可匿名读；客户内容一格不动。

**Non-Goals:**

- 不做匿名**订阅**（匿名访客不能订阅、不能复制、不能收藏）。要这些就登录。
- 不做客户产物的任何匿名暴露，包括「摘要级」暴露（连标题都不给）。
- 不做官网页面本身（属 `official-web-showcase`，本变更只交付稳定端点与形状）。
- 不做看板的自动行业扩产（把 108 个源单元逐个做成看板是内容工作，不是本变更
  的代码量；本变更只保证**通道**存在且可重复执行）。
- 不改既有登录市场端点的鉴权强度。

## Decisions

### D1：平台租户是普通 customer 行，标识用固定 name

平台租户 = 一行 `billing_customers`，`name = "finddata-official"`，
`plan` 挂免费档（它不需要额度，也不该消耗任何客户的额度）。

判定 SHALL 走 `customer.name == "finddata-official"`。

**为什么用 name 而不是新加一列 `is_platform`**：`billing_customers.name` 已有
全表唯一索引（迁移 0037），天然可作稳定标识；加列要写迁移且要为「一行都没有」
的历史库准备回填。用 name 判定零迁移。

**代价**：name 是唯一索引但语义上「名字」可能被运维改。缓解——判定集中在一个
常量与一个 helper 里（`PLATFORM_PUBLISHER_NAME` / `is_platform_publisher()`），
改名单点可查；并在测试里锁死该常量。

### D2：匿名橱窗走独立路由，不给既有端点加可选鉴权

新路由前缀 `/api/v1/showcase/*`，与 `/api/v1/market/*` 完全分离。

**为什么不复用 market 端点加 `Optional[Depends]`**：可选鉴权意味着「漏写
依赖」这种最常见的代码错误会**静默降级为公开**。用独立路由，客户的产物在
物理上就不在这条路径的查询范围里——红线由路由边界保证，而不是由参数正确性
保证。这与项目既有的「SQL 层只查 market 档」「不靠前端过滤」是同一种思路。

**代价**：两处都要维护列表/详情逻辑。缓解——把查询构造抽成一个带
`publisher_filter` 参数的共享函数，两个路由各自传入自己的过滤条件。

### D3：橱窗详情返回完整 spec（含快照），与登录市场详情口径有意分叉

登录市场详情只给 `{id,type,title}`（Q8 红线，防止未订阅者白拿数据）。橱窗详情
给完整 spec。

**为什么这里可以给**：橱窗里只有平台自有内容——数据本来就是我们自己的，且
这份数据是要给全世界看的营销资产。红线保护的是**客户数据**，不是平台自己的
内容。这不是放松，是「红线适用范围」的明确化。

**风险与缓解**：两套详情形状并存容易被误用。缓解——橱窗详情处理器**先断言**
`is_platform_publisher(artifact.customer_id)` 再返回 spec，断言失败一律 404
（不是 403：403 会泄露「这里存在一个客户产物」）。

### D4：导入器以外部的稳定 slug 为幂等键

`dashboards/*.spec.json` 文件里没有 slug 字段，但文件名（`intl-six-country`、
`macro_cn`）本身稳定。导入器用**文件名归一化后的 slug** 作为幂等键，存在
产物的一个保留字段里（`artifact.status_history` 不合适——那是状态迁移记录；
用 `spec.spec.showcase_slug`，属 v2 spec 的自由扩展位）。

**为什么不用标题匹配**：标题会改（改名、翻译），改一次就重复建一份。

**为什么放在 spec 里而不是新列**：spec 是自由 JSON，前端渲染器宽容忽略未知
字段；加列要迁移且只为导入器服务。**代价**是导入器查重必须扫 spec——用
`title` 前缀 + kind 收窄后再比对，量级（十几条）下完全够用。

### D5：导入复用的顺序是「建 draft → 写 spec → publish → 设 market」

全程走既有 service 函数，不直接写表。

**为什么**：`publish_artifact` 与 `set_visibility` 各自带状态机校验与留痕
（`status_history` append-only）。直写表会绕过这些不变量，且未来加校验时
导入器会静默脱队。

**代价**：多次事务往返。十几条看板、一次性执行，可接受。

### D6：橱窗端点限流与缓存照分享端点的骨架

独立 env（`FD_WIRE_SHOWCASE_RATE_PER_HOUR`，缺省保守值），60 秒进程内短缓存，
缓存键含列表参数。

**为什么**：官网静态构建会在构建期抓一次，但真实流量是公网访客直连；没有
限流就是一个匿名可打的查询入口。分享端点已经趟过这条路，直接沿用同一套模式
（含「缓存命中零查询」的实现位置）。

## Risks / Trade-offs

- **平台租户行不存在时全员 500** → 匿名端点对「平台租户缺失」的处置是返回
  空列表而非报错（安全方向：宁可橱窗空，不可服务挂）。导入器则显式报错并
  提示先建租户。

- **客户产物意外进入橱窗**（最严重的失败模式）→ 三重防线：①路由物理分离；
  ②查询层强制 `customer_id = 平台租户`；③橱窗详情处理器先断言再返回，断言
  失败 404。测试必须覆盖「客户 market 产物在橱窗不可见、不可计数、不可推断」。

- **`name` 被运维改动导致橱窗突空** → 常量单点定义 + 测试锁死 + 缺失时安全
  降级为空列表（不 500），故障表现是「橱窗空了」而非「数据泄露」。

- **两套详情形状并存被误用**（有人把橱窗详情接到客户产物上）→ 断言 + 404；
  代码注释显式写明两套口径与原因。

- **快照陈旧**（橱窗展示的是发布时刻数据）→ 沿用既有 `refreshed_at` 字段如实
  呈现「数据截至」；不在橱窗页做自动刷新（匿名访客不该触发引擎调用）。

- **导入器污染生产**（对着生产库误跑）→ 幂等键 + 显式 `--dry-run`；且导入
  只写平台租户名下的产物，物理上碰不到客户数据。

## Migration Plan

1. 建立平台租户行（一次性引导脚本或迁移数据行，幂等 upsert）。
2. 上线后端橱窗端点（此时橱窗为空——安全默认）。
3. 执行导入器把成品看板上架（`--dry-run` 先看报告，再实跑）。
4. 上线前端 `#/showcase` 与市场「平台自营」徽标。
5. 回滚：下架所有平台产物（改 visibility=private）即让橱窗变空；端点本身可
   保留无害。前端回滚镜像即回到无橱窗版本。

## Open Questions

- 平台租户该用哪个 `plan_id`？（免费档足够——它不产生计量。实施时若发现
  额度校验路径会拦，再决定是否新增一个 `internal` 档。）
- 橱窗列表的默认排序（更新时间 vs 人工权重）？可用 `published_at` 起步，
  人工排序属内容运营工具，不阻塞本变更。
